# 功能排班与信息架构

界面好不好用，八成不取决于组件写得多漂亮，而取决于「什么信息放在哪一页、第几屏、第几个位置」。这份文档只讲排班决策，不讲组件 API。规则来自两个真实工程：

- `zyl6932/vcut_lower`（电池解容工具）：4 标签 主页/功能/设置/关于，图标 `MiuixIcons.Home / Tune / Settings / Info`，`HorizontalPager` + `NavigationBar`，底栏点击用 `PagerNavigationSpringSpec` 弹簧 `scroll`，`BackHandler` 非首页时回首页。
- `zyl6932/HyperMusicCover`（HyperOS 4 音乐锁屏模块）：同样 4 标签，功能页每个功能一张 `Card` + 一行 `ArrowPreference`，点进去是**独立 Activity**，不是就地换页。

目标：把「人类直觉」翻译成可执行的判定规则。凡是「看情况」「按设计」，都改写成条件分支。

## 1. 标签页硬规则

### 1.1 数量：3 到 5 个

| 数量 | 判定 | 处置 |
|---|---|---|
| 1 | 单页应用 | 去掉底栏 |
| 2 | 底栏成本高于收益 | 合成一页，页内用 `TabRow` |
| 3–5 | 正常 | 直接用 `NavigationBar` |
| 6+ | 数不过来，也记不住位置 | 最低频的两三个收进「我的」或「设置」二级页 |

底栏的成本是「在拇指区扫一遍再定位」。超过 5 个，第 6 个位置已落在拇指自然弧线外，点击率断崖下降。

### 1.2 并列性：每个标签要能回答「为什么和别的并列」

判断方法：标签名连起来读，看是否像同一张列表的项。

- 合格：`主页 / 功能 / 设置 / 关于` —— 四个都是应用层一级去处，两两之间无包含关系。
- 合格：`首页 / 发现 / 我的` —— 内容型三件套，都是信息入口。
- 不合格：`主页 / 功能 / 设置 / 主题设置` —— 「主题设置」是「设置」的子集，并列意味着用户不知道点哪个。

**反例规则**：若 A 的行为在逻辑上属于 B 的子页，就不能并列。二选一：把 A 降级成 B 下的 `ArrowPreference` 二级页（推荐）；或把 A 提升到同层（「主题设置」改叫「个性化」，真的把壁纸、图标包、字体都放进去）。反例的典型来源是「先做了主题页，后补了设置页」，于是一个挂底栏一个也挂底栏，发版前必须清掉。

### 1.3 一致性

图标取自 `MiuixIcons` 同一族（全实心或全线性），案例用 `Home` / `Tune` / `Settings` / `Info`；文案统一 2–4 字，不要「功能」和「个性化外观设置」并排；每个标签都要有自己的空态（第 7 节），不留「点进去什么都没有」的标签。

## 2. 四个标准标签的语义边界

四个标准标签不是必须全用，但只要用了，就按这里的边界收内容，否则用户的心智模型会碎。

| 标签 | 收什么 | 绝不放什么 | 图标 |
|---|---|---|---|
| **主页** | 当前状态、主操作、关键数据摘要、最近动态 | 全量列表、设置项、许可信息、需要长滚的说明文 | `Home` |
| **功能** | 功能入口清单，一行一个，点进去是完整流程 | 功能参数表单（属二级页）、状态展示（属主页） | `Tune` |
| **设置** | 开关、跳转项、分组偏好、危险操作 | 业务数据、功能入口、版本号之外的元信息 | `Settings` |
| **关于** | 应用图标、版本、开源许可、致谢、反馈渠道 | 设置开关、需要频繁操作的入口 | `Info` |

### 2.1 主页：只回答「现在怎么样」

用户每次打开第一眼看到的东西，只承担一个任务：3 秒内知道**当前状态**和**下一步能做什么**。收状态卡（成功/失败/进行中）、主操作、关键数值、设备或账号摘要；不收完整功能列表、需要决策的选项。口诀：元素的存在意义若是「让用户操作」而不是「告诉用户现在如何」，它就不该在第一屏。

### 2.2 功能页：只做分发，不做执行

功能页是目录，不是工作台。收每个功能一张 `Card`，卡内一行 `ArrowPreference`（标题 + 摘要 + 箭头），点击进**独立 Activity**；不收参数编辑控件（开关、滑块、输入框一律放二级页），不收功能执行结果（回主页状态卡或留在二级页）。

**为什么是独立 Activity**（HyperMusicCover 的明确取舍）：转场动画、返回手势、Android 13+ 预测性返回动画全部由系统在 Activity 切换时免费提供。用 Compose 内部状态就地换页，这三样都得手写模仿且永远模仿不全——预测性返回需要系统提前知道返回目的地，纯 Compose 状态拿不到。

### 2.3 设置页：只放「改了会生效且会持久」的东西

收 `SwitchPreference`、`ArrowPreference`、`WindowDropdownPreference`、危险操作；不收展示性信息（版本号归关于页）、功能入口（归功能页）、需要联网加载的内容。特殊：主题这类**会重绘整个 App** 的设置在案例里单独开 `ThemeActivity`，主界面用 `onResume` 让 `settingsEpoch` 变化从而重读配置——切主题要重建 Composition 树，在设置页内切会连带重置当前页状态，体验割裂。

### 2.4 关于页：只放「不常变、不需要操作」的东西

收应用图标、应用名、版本号（含构建号）、开源许可列表、致谢、反馈邮箱或链接；不收任何开关、任何需要频繁点击的按钮。隐藏入口（开发者选项、日志导出）做成连点版本号触发，不在界面上显式出现。

### 2.5 产品类型变体

| 产品类型 | 标签组合 | 职责分工 |
|---|---|---|
| 工具型（默认） | 主页 / 功能 / 设置 / 关于 | 见上表 |
| 内容型（资讯、社区、视频流） | 首页 / 发现 / 我的 | 首页=推荐流；发现=分类与搜索；我的=个人数据与设置入口 |
| 媒体型（播放器、音乐） | 播放 / 列表 / 我的 | 播放=当前媒体与大控制；列表=队列与歌单；我的=库与设置 |
| 极简工具 | 主页 / 设置 | 功能并入主页，用卡片分组代替独立标签 |

内容型与媒体型都把「设置」降级成「我的」里的 `ArrowPreference`，因为高频动作是消费内容而非调参数。工具型相反：参数就是产品本身，设置必须是一级标签。

## 3. 顺序原则

### 3.1 排序公式：使用频率 × 首次理解成本

- **使用频率**：用户每次会话点它的概率，越高越靠前。
- **首次理解成本**：新用户不看说明能否猜到里面有什么，成本越低越靠前——先帮用户建立「这个应用怎么用」的模型。

两者都高放最前，都低放最后。冲突时频率优先，因为老用户次数远超新用户。

### 3.2 三条固定位

| 位置 | 固定内容 | 理由 |
|---|---|---|
| 第一个 | 主页 / 首页 / 播放 | 启动默认落点，必须最高频且最自解释 |
| 倒数第二个 | 设置 | 低频但位置要稳，用户会形成「设置总在靠右第二个」的肌肉记忆 |
| 最后一个 | 关于 / 我的 | 最低频；内容型的「我的」是个人数据入口而非高频消费入口 |

中间位置留给「功能」「发现」「列表」这类进可攻退可守的标签。

### 3.3 反例

- **设置放第一、关于放第二**：第一眼是开关列表，用户不知道这应用干什么，直接流失；关于页信息量极低，占黄金位置等于浪费一次点击。设置是「用一段时间才会去的地方」，不是门面。
- **按开发顺序或拼音排**：先写的排前，用户看到的顺序和需求无关；底栏是空间记忆不是检索，中文用户不会按拼音找标签。

### 3.4 落地到代码

`HorizontalPager` 页序、`NavigationBar` item 序、图标数组、文案数组必须由同一份数据源派生，不要写四份平行字面量——改一处漏三处就会「点设置跳到关于」。案例做法：定义 `data class Tab(val label: String, val icon: ImageVector)` 列表，两个组件都 `forEachIndexed` 遍历它。

## 4. 单页信息排班

标签决定「哪一页」，这一节决定「页内怎么排」。

### 4.1 黄金顺序

```
状态 → 主操作 → 数据/内容 → 次要信息 → 元信息
```

| 层级 | 内容 | 视觉权重 |
|---|---|---|
| 状态 | 现在是什么情况：成功、失败、进行中、空 | 最高，大色块 |
| 主操作 | 用户最可能做的那件事，通常一个按钮 | 高，主色填充 |
| 数据/内容 | 具体数值、列表、明细 | 中，卡片分组 |
| 次要信息 | 补充说明、辅助操作、历史记录 | 低，常规字号 |
| 元信息 | 版本、更新时间、来源标注 | 最低，小字灰色 |

理由：视线从「我遇到什么问题」→「我能做什么」→「细节是什么」→「这些数字哪来的」。顺序颠倒会让用户前三屏都找不到重点。

### 4.2 一张卡只装一类信息

- 状态卡只装状态，不塞开关；数据卡只装同类数据，「电量」「温度」「循环次数」不要和「Wi-Fi 名称」同卡。
- 设备信息卡单独一张：它唯一的用途是「排查时截图给客服」，与日常使用无关。

案例主页正好是这个顺序：第一张状态卡，之后数据卡（`BasicComponent` 多行），最后设备信息卡。

### 4.3 首屏不超过 3 张卡

超过 3 张，用户要滚动才能看全，而「需要滚动」本身就是决策成本——他不知道下面还有没有更重要的。内容确实超了：第 4 张之后收进二级页，用一张 `ArrowPreference` 卡做入口；或把同类卡合并成一张多行卡（`BasicComponent` 每行一条）。

### 4.4 状态卡范式

```
大色块（成功绿 / 失败红 / 进行中蓝）
  ├─ 图标（勾 / 叉 / 转圈）
  ├─ 标题（一句话结论：「已解容」「解容失败」）
  ├─ 副标题（下一步动作：「点击刷新」「检查 USB 连接后重试」）
  └─ 左下角（应用名或数据来源）
```

- **点击即刷新**：整卡是可点区域，不需要额外刷新按钮。案例里点状态卡就是手动刷新。
- **副标题必须给动作**，不能只报错：「解容失败」是错的，「解容失败，请检查 USB 连接后重试」才对。
- **颜色只表达成败**：状态卡用语义色，不用主题主色，否则用户无法从颜色判断结果。

## 5. 二级页 / 就地展开 / 弹窗 判定

按第一列从上往下匹配，命中即停。

| 场景特征 | 选型 | 组件 | 理由 |
|---|---|---|---|
| 完整流程、多步操作、有自己的返回栈 | **独立 Activity** | 新 Activity + `NavTransitions` | 转场、返回手势、预测性返回全由系统提供 |
| 一次确认、一次性输入（删不删、输个名字） | **WindowDialog** | `WindowDialog` | 不依赖 Scaffold，独立 Activity 里也能用 |
| 多选一、轻量编辑（排序、选标签） | **BottomSheet** | `OverlayBottomSheet` | 底部升起，拇指可达，可拖动关闭 |
| 只展开 1–2 行补充信息 | **就地展开** | `AnimatedVisibility` + 卡内内容 | 不打断上下文，用户不用记原位置 |

### 5.1 必须用 Activity 的四个信号

满足任意两条：页面有自己的二级结构（页内还能再进一层）；用户可能中途返回，且返回后应回到原来那页的滚动位置；内容需要独立于主页的生命周期（申请权限、绑前台服务）；页面足够重，值得一次完整转场来建立空间感。

### 5.2 坚决不用 Activity

只问「确定删除吗」用 `WindowDialog`——用 Activity 会让返回手势变得莫名其妙；只从 5 个标签选 1 个用 `OverlayBottomSheet`；只显示两句解释用就地展开，连弹窗都不需要。

### 5.3 两套弹窗不要混用

`OverlayDialog` / `OverlayBottomSheet` 依赖 `Scaffold` 的 `popupHost`，适合主界面内；`WindowDialog` 不依赖 `Scaffold`，适合独立 Activity 或无 `Scaffold` 的上下文。同一个工程可以两者都有，但**同一种交互只用一种**。不要「删除在主页用 Overlay、在二级页用 Window」，用户会觉得是两个应用。

### 5.4 就地展开的边界

就地展开只用于「补充信息」，不用于「操作」。一旦展开区里出现需要提交的控件（输入框 + 保存），就升级成 BottomSheet 或 Activity——提交失败时需要错误提示位置，就地展开没有空间承载错误态。

## 6. 设置项排班

设置页的项数会随时间线性增长，是最容易乱的地方。

### 6.1 组内顺序：开关在上、跳转在中、危险在下

| 位置 | 类型 | 组件 | 理由 |
|---|---|---|---|
| 组内上部 | 开关类 | `SwitchPreference` | 改完立刻看效果，不需离开页面 |
| 组内中部 | 跳转类 | `ArrowPreference` / `WindowDropdownPreference` | 需离开或弹选择，成本居中 |
| 页面最底 | 危险操作 | `ArrowPreference` + 红色标题 | 需二次确认，放最不易误触的位置 |

### 6.2 分组：SmallTitle + Card，每组 ≤ 6 行

分组标题用 `SmallTitle`，它自带与上方内容的间距，不要再补 `padding`；每组包一张 `Card`，行间用 `HorizontalDivider`；**每组 ≤ 6 行**，超过说明这组混了两个概念，应该拆——6 是「一眼扫完不用数」的上限；组的顺序也按频率，最常改的组在上。

案例的分组：`界面`、`诊断`、`模块`、`应急`——分别对应外观偏好、排查工具、功能开关、出事时的救命操作，边界清晰无交叉。

### 6.3 危险操作三件套

1. **单独分组并置底**，不与普通开关混排；
2. **文案动词开头且说清后果**：「清除全部记录」而不是「清理」；
3. **二次确认**：`WindowDialog` 标题说清后果，按钮是动词（「清除」/「取消」）而非「确定」/「取消」。

高危且不可恢复的再加一层：输入确认词或长按 3 秒。

### 6.4 值展示

- 当前值放 `summary`（`ArrowPreference` 第二行），不要另起一列；数值用等宽字体，避免跳动。
- 枚举型（语言、主题模式）用 `WindowDropdownPreference`，选中后 summary 立刻变新值。

## 7. 空态 / 加载态 / 错误态

只要页面会加载数据，三态必须都设计，不能只做成功态。

| 态 | 表现 | 文案要求 |
|---|---|---|
| 空态 | 图标 + 一句说明 + 一个行动按钮 | 说清「为什么空」和「怎么让它不空」 |
| 加载态 | 骨架屏或 `CircularProgressIndicator`，占位尺寸与最终内容一致 | 短内容用行内指示，不要整屏「加载中…」 |
| 错误态 | 图标 + 结论 + 原因 + 重试按钮 | 三段式：发生了什么 / 为什么 / 怎么办 |

共同禁忌：只给图标不给文字；只给「出错了」不给原因；只给原因不给下一步。

### 7.1 骨架屏优先于转圈

结构固定的页面（列表、卡片）用骨架屏，它能提前告诉用户「这里会有几行」。只有一个整体结果的（一次检测）才用转圈。骨架屏占位尺寸必须与最终内容一致，否则加载完会跳动，这种跳动比多等 200ms 更难受。

### 7.2 状态卡承载错误态

主页的错误不要用弹窗——弹窗打断用户且关掉就没了。正确做法是画进状态卡：色块变红、图标变叉、标题写结论（「读取失败」）、副标题写下一步（「检查设备连接后点击重试」）、整卡可点重试。这样错误信息持久、可恢复、不打断流程。

### 7.3 空态按钮是「创建」不是「刷新」

刷新是把问题推回给用户，创建是帮用户往前走。

## 8. 导航手势与返回键契约

### 8.1 一级标签：非首标签按返回回首页

底栏标签平级，没有天然返回栈，但用户预期「退出应用」之前先回起点：当前不在第一个标签 → 返回键切回第一个标签（案例：`BackHandler(enabled = index != 0)`）；当前在第一个标签 → 交给系统（退出应用）。不要维护标签间历史栈（A→B→C 返回回 B 再回 A），那会让返回键不可预测。

### 8.2 二级 Activity：用系统返回，不要拦

进入独立 Activity 后，返回键、返回手势、预测性返回动画全由系统处理，**不要写 `BackHandler`**。自己拦截会破坏预测性返回的动画预览（系统在动画开始前就不知道要回哪），表现为「返回时闪一下」或「动画方向错」。

### 8.3 预测性返回不要自己实现

Android 13+ 的预测性返回需要系统在用户刚开始滑动时就拿到「返回到哪个界面」，这个信息只有 Activity/Fragment 返回栈能提供。纯 Compose 状态切换拿不到，手写动画只是模仿，且会在系统真正执行返回时被打断。需要预测性返回的页面，就做成独立 Activity（对应 5.1 第一条）。

### 8.4 滑动关闭要显式开启

`miuix-nav` 的 `swipeDismiss` 默认 `None`，内置转场预设也不会自动开启，按路由显式指定：普通二级页用 `NavSwipeDirection.LeftToRight`（LTR）；底部 Modal 用 `NavSwipeDirection.TopToBottom`。`NavSwipeDirection` 是物理手指方向，不随 RTL 镜像，RTL 下返回方向写 `RightToLeft`。

### 8.5 底栏点击动画

同标签重复点击不处理（或滚回顶部），跨标签切换用弹簧：案例给 `HorizontalPager` 的 `scroll` 用 `PagerNavigationSpringSpec`，效果是「点一下页面弹过去」，比线性滚动更符合物理直觉。

## 9. 排班自查表

发版前逐条过一遍，全通过才算排班合格。

| 检查项 | 正确做法 | 常见错误 |
|---|---|---|
| 标签数量 | 3–5 个 | 6 个以上挤在底栏，字被截断 |
| 标签并列性 | 每个都是同级去处 | 「设置」和「主题设置」并列 |
| 抽象层级 | 同一粒度（都是应用级去处） | 「主页」与「高级诊断工具」并列 |
| 排序 | 频率 × 理解成本；主页第一、设置倒二、关于最后 | 按开发顺序或拼音排 |
| 数据源 | 标签定义只写一份，Pager 与底栏共享 | 四份平行数组，改一处漏三处 |
| 图标一致 | 同一族（全实心或全线性） | 三个线性混一个实心 |
| 主页首屏 | ≤ 3 张卡 | 滚三屏才看到主操作 |
| 卡内容纯度 | 一张卡一类信息 | 状态卡里塞开关 |
| 主页顺序 | 状态 → 主操作 → 数据 → 次要 → 元信息 | 版本号放最上面 |
| 状态卡 | 大色块 + 结论 + 下一步，整卡可点刷新 | 只写「出错了」，无重试入口 |
| 二级页选型 | 完整流程用 Activity | 复杂表单塞进弹窗 |
| 弹窗选型 | 确认用 `WindowDialog`，多选用 `OverlayBottomSheet` | 用 Activity 做一次确认 |
| 弹窗一致性 | 同一交互只用一种弹窗体系 | 同一功能两页用了不同弹窗 |
| 就地展开 | 只展开补充信息 | 展开区里放提交表单 |
| 设置组内顺序 | 开关 → 跳转 → 危险 | 危险操作插在开关中间 |
| 设置分组 | `SmallTitle` + 每组 ≤ 6 行 | 一组 12 行，扫不完 |
| 危险操作 | 单独分组置底 + 二次确认 + 动词文案 | 与普通开关同组，点一下就执行 |
| 空态 | 图标 + 说明 + 行动按钮 | 白屏，或只有「暂无数据」 |
| 加载态 | 骨架屏尺寸与最终内容一致 | 转圈居中，加载完内容跳动 |
| 错误态 | 结论 + 原因 + 重试 | 只弹一个「网络错误」 |
| 返回键（一级） | 非首标签返回回首页 | 在标签间维护历史栈 |
| 返回键（二级） | 交给系统，不写 `BackHandler` | 自己拦截，破坏预测性返回 |
| 滑动关闭 | 按路由显式配 `swipeDismiss` | 以为预设自动开启，结果关不掉 |
| 主题类设置 | 单独 Activity + `onResume` 重读 | 页内切主题导致页面状态被重置 |
